# v1.1 proposal: an MCP control layer for generated projects

**Status: proposal, not implemented.** It needs maintainer approval before any code is written.
Target release: v1.1.0, a MINOR release: additive, with no change to defaults (see
[VERSIONING.md](VERSIONING.md)).

## Goal
An MCP-compatible AI client (Claude, ChatGPT, Cursor, or any other MCP host) can **operate a
generated project through a standard protocol**: discover its state, run its checks and read its
knowledge, without knowing its shell commands.

Today an agent must learn `./dev`, `tools/ai-*` and their flags from the docs. The clean-room
runs showed this works, but it costs about 10–20 minutes of orientation and some guessing. MCP
turns those operations into typed, permission-scoped tools.

Non-goals:
- **No new source of truth.** No database, no daemon state, no copy of the project state.
- **No code editing through MCP.** Editing stays with the client's own file tools.
- **No remote control of production systems.**

## Design principles
1. **Thin adapter over the existing protocol.** Every tool calls the same tools a human runs:
   `tools/ai-check`, `tools/ai-map`, `tools/ai-task`, `tools/ai-validate`, `./dev`,
   `scripts/create-project`. State stays in `.ai/` (ai-project-template 1.2.0), and MCP never
   writes it directly.
2. **Upstream first.** The generic part (protocol state and validation) belongs in
   ai-project-template as `tools/ai-mcp`, so every template project gets it. The blueprint only
   adds an extension with its own tools (profiles, benchmarks, health, generation).
3. **Explicit capability tiers.** Every tool is either *read-only* or *mutating*, declared in its
   MCP annotations and enforced by the server, not just documented.
4. **Allowlists, not shells.** No tool accepts arbitrary commands, paths outside the project, or
   free-form arguments that reach a shell.

## Architecture
```text
MCP client (Claude / ChatGPT / Cursor / …)
        │  MCP (JSON-RPC 2.0) — stdio by default
        ▼
tools/ai-mcp  (Python stdlib, like the other tools/ai-*; no new runtime dependency)
   ├─ protocol tools  → tools/ai-check --json, ai-map, ai-task, ai-validate --json   (template)
   ├─ project tools   → ./dev status|test|benchmark, health endpoints                (blueprint extension)
   ├─ generator tool  → scripts/create-project                          (blueprint repository only)
   └─ resources       → AI_PROTOCOL.md, .ai/config/project.json, .ai/state/*, .ai/knowledge/**
```
The server is a stateless process started per session. It is configured by
`.ai/config/mcp.json`, which is tracked: enabled tools, path roots, limits. That file is
validated by `ai-check` like the other config.

## Tools

R = read-only (`readOnlyHint: true`). M = mutating (`readOnlyHint: false`). Destructive actions are
not offered at all.

| tool | tier | wraps | notes |
|---|---|---|---|
| `get_project_state` | R | `ai-check --json`, `.ai/state/STATUS.md` | the eight state questions, check results, warnings |
| `get_architecture` | R | `project.json → architecture`, `ARCHITECTURE.md` | profile, components, enabled modules, ADR index |
| `get_current_task` | R | `ai-task current` / `ai-task show` | the active task packet: objective, acceptance, validation |
| `list_tasks` | R | `ai-task list` | filter by status |
| `search_project_knowledge` | R | ripgrep-style search over `.ai/knowledge/**`, `docs/**`, `AI_PROTOCOL.md` | bounded results with file:line; never searches outside these roots |
| `list_validation_commands` | R | `ai-validate --list` | ids, stages, confirmed flags |
| `list_profiles` | R | `docs/BLUEPRINT_CAPABILITY_MATRIX.md`, `create-project --help` | profiles, auth profiles, modules |
| `inspect_health` | R | `./dev status`, `GET /readyz` on the **internal** ops port | per-dependency status; never exposes secrets |
| `run_ai_check` | R | `ai-check --json` | pure check |
| `run_ai_map` | M | `ai-map` | writes `.ai/map/` (gitignored) |
| `run_validation` | M | `ai-validate --json --only <id>…` | ids must be confirmed commands; long-running → MCP progress notifications |
| `run_tests` | M | `run_validation` limited to stage `unit`/`integration` ids | convenience preset |
| `run_benchmarks` | M | `./dev benchmark --smoke` (full mode needs `confirm: true`) | heavy; one at a time; writes `benchmarks/results/` |
| `task_transition` | M | `ai-task start/block/unblock/complete` | the only way MCP changes task state; `complete` requires evidence strings, exactly as the CLI |
| `create_project` | M | `scripts/create-project` | **blueprint repository only**; destination must be under configured roots and empty |

### Resources and prompts
- **Resources (read-only):** `ai://protocol` (AI_PROTOCOL.md), `ai://project` (project.json),
  `ai://status`, `ai://roadmap`, `ai://knowledge/{file}`, `ai://adr/{id}`. These are documents,
  so clients can load them as context instead of calling tools.
- **Prompts:**
  - `start_work`: the protocol's "start here" sequence;
  - `add_feature`: points at `docs/examples/adding-a-feature.md` and the authorization recipe;
  - `prepare_release`.

## Transport and modes
| mode | transport | default | for |
|---|---|---|---|
| **Local** | stdio, launched by the client (`python3 tools/ai-mcp --root .`) | **yes** | an agent on the developer's machine |
| **Remote (opt-in)** | Streamable HTTP, bound to `127.0.0.1` unless explicitly configured | no | a hosted agent or IDE in a dev container or remote workspace |

Remote mode is never on by default and never bound to a public interface without an explicit
`--listen` flag *and* authentication configured. The server refuses to start in remote mode
without auth.

## Authentication and permissions
- **Local (stdio):** the trust boundary is the OS user who started the client. It holds no
  credentials of its own.
- **Remote:** OAuth 2.1 per the MCP authorization spec. The server is an OAuth resource server:
  it validates bearer tokens (audience = this server) from the configured issuer, which can be
  the project's own OIDC provider. A static per-session bearer token is allowed only for
  localhost. Tokens are never logged.
- **Scopes map to tiers:**
  - `mcp:read` → R tools and resources;
  - `mcp:run` → `run_*` tools;
  - `mcp:tasks` → `task_transition`;
  - `mcp:generate` → `create_project`.

  `.ai/config/mcp.json` can disable any tool, whatever the scopes.
- **Human in the loop:** M tools carry annotations, so clients that support confirmation prompt
  the user. `run_benchmarks` in full mode and `create_project` also require an explicit
  `confirm: true` argument.

## Security model
| threat | control |
|---|---|
| arbitrary command execution | no shell strings; only confirmed validation ids from `project.json` and fixed argv templates; inputs validated by schema and regex |
| path traversal / writing outside the project | every path is resolved and must stay under `root` (or the configured generation roots for `create_project`); symlinks resolved first |
| secret disclosure | output tails pass through a redactor (`APP__*` secret keys, `.env*`, tokens, private keys, gitleaks patterns); `.env` files are not searchable resources |
| resource exhaustion | per-tool timeouts (from `timeout_s`), output caps (8 KiB tail, 50 search hits), one mutating operation at a time (lock file) |
| prompt injection via repository content | tool results are returned as data; the server never executes instructions found in files. The protocol's authority order (AI_PROTOCOL.md §2) applies |
| privilege escalation via task state | `task_transition` uses `ai-task`'s state machine; no direct `.ai/` writes |
| outward actions | no tools for git push, publishing, deploying or network calls beyond local services |
| auditability | every call is appended to `var/mcp-audit.jsonl` (gitignored): tool, arguments (redacted), duration, result status |

## Generated projects
`create-project` includes `tools/ai-mcp` and `.ai/config/mcp.json` in every generated project,
with:
- `create_project` disabled (it is blueprint-only);
- the tool set matching the project's selected modules (for example, no NATS health without
  `messaging_nats`).

`scripts/validate-generated` gains MCP checks, so the generator stays honest.

## Risks
- **Spec churn:** MCP transports and auth are still evolving. Mitigation: a stdio-first, minimal
  surface, conformance tests against the official inspector, and the spec version pinned in
  `mcp.json`.
- **Duplicate surface:** two ways to run things (CLI and MCP) could drift. Mitigation: parity
  tests compare MCP results with CLI output for every tool.
- **Over-permissioned clients:** users may grant everything. Mitigation: conservative defaults
  (R plus `run_validation` only), and M tools are visibly labelled.
- **Template coupling:** the generic part lives upstream, so ai-project-template needs a release
  first. This proposal depends on that.

## Acceptance criteria
1. **Protocol:** passes the MCP inspector / conformance checks over stdio; and over Streamable HTTP
   with auth when remote mode is enabled.
2. **Parity:** for each tool, MCP output equals the corresponding CLI output, including `run_validation` on all confirmed commands.
3. **Security tests:**
   - path traversal rejected;
   - unconfirmed or unknown command ids rejected;
   - secrets redacted (seeded `.env` and `APP__AUTH__*` values never appear);
   - R tools leave the working tree byte-identical (hash before and after);
   - remote mode refuses to start without auth;
   - tokens with insufficient scope are denied.
4. **Generated projects:** `validate-generated` passes for the three reference profiles, with MCP
   enabled and `create_project` absent.
5. **Clean-room run 3:** an agent given only a generated repository and the MCP server builds a
   feature, and reaches `run_validation` green and `task_transition complete`. Its orientation
   time and friction are compared with runs 1 and 2.
6. **Docs:** `docs/AI_AGENT_GUIDE.md` gains a client-setup section (Claude Code, Cursor, and a
   generic MCP host), and `SECURITY.md` covers MCP.
7. **Versioning:** shipped as v1.1.0. No v1.0.x default changes.

## Effort estimate
- Template `tools/ai-mcp` (stdlib JSON-RPC over stdio, generic tools and resources): about 2 days.
- Blueprint extension, generator integration and tests: about 2 days.
- Remote mode with OAuth: about 2–3 days. It can ship later, in v1.1.x.
